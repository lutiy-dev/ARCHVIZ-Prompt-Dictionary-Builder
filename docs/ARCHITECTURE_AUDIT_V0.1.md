## Дефекты и ограничения

### Блокируют production-квалификацию

1. Нет prerequisites: `brick` один компилируется без source, Geometry Lock и области. Требуется определить минимальный контракт каждого task/preset, а не автоматически вставлять невидимые ограничения.
2. Нет scope: `facade` ограничивает изменения стенами, но `wet` меняет землю. Исходная цепочка Facade + Wet Surface требует явно двух областей или двух проходов. `polish + brick` тоже не даёт warning, хотя «tonal only» и замена материала несовместимы.
3. Конфликты не полны. Алгоритм проверяет `b.id < conflict`: при односторонней декларации конфликт может исчезнуть. Нужны проверка симметрии либо независимый от направления сбор пар.
4. Сохранения не закрепляют текст/version/library revision. Обновление базы меняет результат старого пресета. Это блокирует повторяемость production workflow.
5. Непроверенная библиотека может потерять инструкцию: неизвестная section молча исключается; при отсутствующем параметре используется пустая строка. Проверять схему и ссылки перед открытием Composer.

### Исправить до публикации и UI test

6. Пустое значение параметра допустимо в UI и даёт `with , ...`. Нужна проверка trim/длины/формата на входе; defaults не менять автоматически.
7. Import validation использует `k in b.parameters`, включая унаследованные ключи (`toString`); нет строгой проверки объекта parameters. Нужен own-property check и общий validator. DOM использует textContent; подтверждённого XSS этим аудитом не установлено.
8. Повреждение одной localStorage-записи сбрасывает читаемый список целиком; последующее Save может перезаписать прежний массив. Перед ремонтом — экспорт сырой копии, затем восстановление валидных записей.
9. Лимит импорта 200 блоков, но source library не ограничен, UI сборку не ограничивает. Будущая база >200 может экспортировать неимпортируемую сборку. Согласовать лимиты и round-trip.
10. Подписи параметров зашиты в JS, при пополнении базы UI знает лишь четыре ключа. Поля label/type относятся к будущему контракту, не к росту ветвлений в UI.
11. Несколько GOAL допускаются; порядок внутри секции зависит от выбора. Нужна политика cardinality/priority, а не произвольная сортировка текста.
12. Copy блокируется только при известных конфликтах. Экспорт/сохранение конфликтной сборки возможно: это допустимый draft, но его нельзя маркировать готовым prompt.
