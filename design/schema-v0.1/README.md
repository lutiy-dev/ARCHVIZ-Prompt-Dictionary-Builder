# Единая машинно-читаемая база — schema v0.1, DESIGN DRAFT

2026-09-28. Статус проекта контракта: PROPOSED, не подключён к приложению. Это не миграция и не изменение текущего совместимого контракта.

## Разделение версий без неоднозначности

Ранее `schemas/prompt-blocks.v0.1.schema.json` зафиксировал фактический legacy-формат с числовым `schema_version: 1`. Он остаётся без изменений.

Здесь проектируется первая версия общей модели данных для нескольких клиентов: `schema_family: "archviz.prompt-library"`, `schema_version: "0.1.0"`, `kind: "dictionary" | "prompt_blocks"`. Совпадение разговорного названия v0.1 НЕ означает совместимость. Клиент обязан распознавать family + kind + точную версию. Legacy-клиент эти файлы читать не должен. После согласования нужны отдельные migration plan и adapter; никакого автоматического переименования старого schema_version.

## Принцип владения данными

| Сущность | Отвечает за | Не отвечает за |
|---|---|---|
| Dictionary term | Понятие, названия EN/RU, определения, синонимы, категория, связи | Готовый prompt и настройки рендера |
| Prompt block | Одну техническую инструкцию, шаблоны EN/RU, параметры, область, зависимости, эффекты и QC | HTML, компоненты UI, ComfyUI node ID |
| Composition / preset (следующий контракт) | Выбранные ревизии блоков, значения параметров, контекст прохода и input bindings | Копии определений и ручное переписывание шаблонов |
| Adapter / compiler | Проверку контракта, подстановки, канонический порядок, формат вывода | Самовольное изменение знаний и повышение статусов |

Термин может иметь ноль или несколько блоков; блок ссылается на один или несколько терминов через term_refs. Единственный источник связи — prompt block → term. Кнопка Add to Prompt строится по обратному индексу. Если блоков несколько, пользователь выбирает; если нет — карточка остаётся справочной. term.label описывает понятие, block.label — конкретное действие, поэтому они не обязаны совпадать.

Category — словарная классификация. Section — место инструкции в результате. UI строит категории блоков через term_refs, не дублирует category в блоке.

## Пакет

- common.schema.json — общие типы.
- dictionary.schema.json — валидируемая схема словаря.
- prompt-blocks.schema.json — валидируемая схема библиотеки блоков.
- examples/dictionary.json — четыре связанные словарные записи.
- examples/prompt_blocks.json — четыре связанные инструкции: Geometry Lock, граница фасада, кирпич, QC.
- validate-examples.mjs — ограниченный offline validator использованных ключевых слов и предметных правил, с негативными проверками. Это не универсальный JSON Schema validator.

Шаблоны и определения примеров написаны для проверки проекта структуры. Они не заменяют текущие 20 блоков; имеют GENERATED / experimental. Числовой диапазон шва 0–50 мм — иллюстрация ограничения для этого примера, не строительная рекомендация. Defaults для этих параметров намеренно не назначены: значения должен задать автор задания по референсу.

## Словарь

| Поле | Назначение |
|---|---|
| id, revision | Стабильный машинный ID и положительная целочисленная ревизия |
| label.en / .ru | Название понятия |
| definition.en / .ru | Объяснение понятия, не исполняемая инструкция |
| category | Одна из десяти фиксированных категорий |
| aliases.en / .ru | Синонимы для поиска |
| tags | Дополнительные машинные метки |
| related_term_ids | Связанные понятия в том же library revision |
| provenance | authored/adapted/imported, ссылки на источники и примечание |
| quality | Статус содержимого и доказательства отдельно от его production-принятия |

Пример: Geometry Lock — словарное понятие. «Сохранить проёмы» и «Сохранить камеру» впоследствии могут стать разными блоками этого понятия. Не требуется копировать определения в блоки.

## Prompt block

| Поле | Назначение |
|---|---|
| id, revision, label | Идентичность, ревизия, название операции |
| term_refs | ID + точная revision терминов |
| section, order | Машинный код секции и приоритет внутри секции |
| template.en / .ru | Равнозначные технические шаблоны; RU — полный перевод |
| parameters | Именованные типизированные параметры |
| applicability.pass_types | Явный список допустимых типов прохода |
| applicability.scope | any, masked_region или whole_image |
| required_inputs | Обязательные source_image, edit_mask, reference_image с назначением EN/RU |
| requires_all | Точные ревизии необходимых блоков, включая транзитивные зависимости |
| conflicts_with | Явные несовместимые ID, достаточно декларации с одной стороны |
| exclusive_group | Не более одного блока группы в одном проходе, либо null |
| effects.changes / preserves | Машинные токены изменяемых и сохраняемых свойств |
| qc_rules | Структурированные критерии приёмки с методом и уровнем ошибки |
| provenance, quality | Происхождение, проверенность и доказательства |

Никаких seed, denoise, checkpoint по умолчанию в общих текстовых блоках. Это настройки execution profile / workflow / test run. Блоки не содержат имени модели и не обещают универсальной эффективности. Метаданные applicability относятся к задаче и области, а не к подтверждённой совместимости с конкретной моделью.

## Типы параметров

text: требуется max_length; непустая строка, не допускающая `{{` и `}}`.
number / integer: обязательны minimum, maximum; unit — строка либо null для безразмерного значения. minimum <= maximum. Число конечное, integer целое. Единицы записываются в шаблоне, не дописываются компилятором повторно. Ноль допустим только если разрешён диапазоном; предметная корректность проверяется автором.
enum: options содержат стабильный value, label EN/RU и prompt_value EN/RU. В сохранении хранится value, в текст подставляется prompt_value нужного языка. Значения options уникальны.

Все типы имеют required. default необязателен; если присутствует, обязан пройти ту же типовую проверку. Для required без default значение задаётся явно. Для optional без default компилятор использует пустую строку: только автор блока отвечает за грамматику, такой optional placeholder допустим лишь если оба шаблона остаются корректными. Неизвестные параметры запрещены. max_length не применяется к number/enum; минимум/максимум не применяется к строкам. Схема задаёт форму; эти условные ограничения дополнительно проверяет semantic validator.

text-параметры в v0.1 — одинаковая буквальная строка в EN/RU, перевод не выполняется. Поэтому предпочтительны enum и числа. Если текст задан на английском, UI обязан обозначить, что RU-предпросмотр содержит непереведённое значение. Шаблон RU сам по себе не гарантирует перевода пользовательского текста.

## Детерминированная компиляция (контракт, не реализация Composer)

1. Проверить схемы, family/kind/version, одинаковый library_revision словаря и блоков; IDs уникальны в своих сущностях; ссылки разрешаются на точные ревизии. Запретить циклы requires_all, dangling refs, self-conflicts и self-related terms.
2. Принять контекст одного прохода: pass_type, scope, bindings обязательных входов и выбор блоков с revision/parameters. Должен присутствовать source_image. Global и локальная обработка — разные проходы; коллекция проходов будет отдельным форматом pipeline.
3. Проверить applicability, зависимости и входы. Missing dependency = ошибка + понятная подсказка. Не добавлять скрытно блоки или defaults вне объявленного контракта.
4. Проверить конфликты в обе стороны и exclusive_group. На конфликте разных значений одного block ID — остановка и явный выбор, не first-wins.
5. Проверить effects: change X несовместим с preserve X либо родителем/потомком X в том же проходе. Токены иерархические по точке: `facade` охватывает `facade.surface_material`, а `geometry` — нет. Метаданные заполняются и проверяются человеком; парсера смысла текста нет. Новый токен требует согласования словаря свойств, опечатки не считать новым свойством автоматически. Полный реестр effects — открытый пункт до миграции.
6. Проверить параметры, одинаковый набор placeholders обоих шаблонов и точное совпадение с keys parameters. Подставлять только значения, не исполнять код/выражения. Rendering enum зависит от языка.
7. Сортировать по section_order → order → id. Этим порядок результата не зависит от очередности кликов.
8. Удалять только повтор одного ID + revision + одинаковых параметров. Разные ID с похожим или одинаковым текстом не объединять автоматически: сохраняются происхождение и QC. Семантическая дедупликация вне v0.1.
9. Вернуть structured sections, compiled EN/RU, errors/warnings, selected block revisions и список QC. Без ошибок результат технически готов к запуску; это не статус TESTED для prompt.

Поля всех неизвестных объектов/версий запрещены. Ошибки не превращаются в пустые строки/пропущенные секции. template EN/RU предназначены для инструкционных моделей. RESTRICTIONS не следует автоматически отправлять в SDXL negative conditioning: для него нужен отдельный адаптер и отдельные модельные проверки. QC остаётся checklist, не считается выполненным моделью.

## Пример области: исходная цепочка пользователя

Geometry Lock + Facade Material + Old Brick + Preserve Windows совместимы в masked facade pass. Overcast Day и Wet Surface меняют свет/землю вне этой маски. Их нельзя незаметно добавить в тот же локальный проход. Нужно явно выбрать отдельный global lighting / road pass либо спроектировать multi-region contract. В этой версии безопасно возвращать ошибку области, не подменять intent пользователя.

Final Polish не должен принимать material.aged_brick: несовместимы pass_types. Отдельная фасадная ветка + последующий Final Polish возможны только как два прохода, каждый со своими inputs и QC.

## Provenance и проверенность

origin=authored может иметь пустые source_refs: внешний источник не придумываем. Для adapted/imported минимум один реальный источник обязателен.

quality.content_status:
- GENERATED — авторский текст без содержательной приёмки.
- VALIDATED — экспертная проверка смысла, перевода и ограничений, с evidence_refs.
- TESTED — есть реальные прогоны и evidence_refs.

quality.maturity: experimental либо production_standard. Production требует TESTED + evidence_refs + approval_refs. path и SHA-256 доказательств обязательны; существование и хеш проверяются отдельно, одних строк недостаточно. Полные schemas review/test/approval records — следующий контракт до любого повышения статуса. До него все примеры и мигрируемые блоки остаются GENERATED/experimental.

Программная проверка JSON не меняет content_status. Evidence реального теста должна включать версию модели, workflow, inputs/masks/reference, settings, seed, итоговый prompt и результат QC; область применимости остаётся в test profile. Один удачный тест одной модели не делает блок универсальным.

## Версии и переносимость

revision записи увеличивается при любом изменении её полей. ID не переиспользуется. library_revision идентифицирует неизменяемый согласованный снимок обоих файлов; исправление создаёт новый снимок. При компиляции точные revision терминов/блоков обязаны присутствовать в выбранном снимке.

Будущая сохранённая комбинация должна фиксировать schema family/version, Git commit библиотеки (40 hex), library_revision, block ID + revision, parameters, pass context, версию compiler, профиль output adapter и входные привязки. Для воспроизведения используется соответствующий Git snapshot. Недоступный snapshot — ошибка, а не незаметная подстановка latest. Дизайн такого recipe не включён в эти две schemas и не должен подменяться нынешним legacy-export.

UI, ComfyUI и агент читают одни записи. Предпочтительно использовать общий компилятор либо одинаковые conformance fixtures между JS/Python; само наличие JSON не гарантирует совпадения поведения клиентов. ComfyUI adapter преобразует outputs под ноды; агент может предложить выбор, но обязан пройти тот же validator.

## Миграция: НЕ выполнена

| Сейчас | Предложение | Риск |
|---|---|---|
| Dictionary дублирует поля block | Отдельный term + term_refs | Требуется mapping старых ID |
| EN text, русский заголовок | template EN/RU | Переводы требуют сверки смысла |
| Строковые параметры/defaults | Typed parameters | Нужно явное преобразование пользовательских сохранений |
| Свободные label секций | Машинные section codes | Потребуется адаптер UI |
| Неполные conflicts | applicability + dependencies + groups + effects | Ложные запреты возможны при неверной разметке |
| Результат зависит от порядка кликов | section/order/id | Порядок текста изменится после утверждения |
| Один файл wire version 1 | Schema family + kind + version 0.1.0 | Legacy Composer несовместим |

Следующий шаг — согласовать контракт и открытые пункты: effects registry, обязательный состав task/preset, формат доказательств/recipe. Потом mapping/migration на отдельной ветке с backup пользовательских JSON; затем Composer; после — Pages, UI test, prompt tests. До подтверждения не менять текущие /data, /src и /schemas.
